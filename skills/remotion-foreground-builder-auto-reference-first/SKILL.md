# Remotion Foreground Builder Auto — Reference First

## Goal

Before visual directing, ask whether the user wants the raw talking-head recording preprocessed. If yes, create a clean original-resolution base plate with conservative word-safe cuts. If no, preserve the raw file and its timeline unchanged. Use the selected working base and working timeline to build polished Remotion foreground animations and enhance suitable spoken ideas with traceable reference-first H3 scenes, interactions, spatial reveals, contrasts, and mechanisms that improve understanding, feeling, or recall. Accept an optional companion script or subtitle file, but never require the user to prepare segmentation markdown. After this single preprocessing-choice gate, continue through the final composite without intermediate approval gates unless a real meaning, cost, workflow, or missing-asset blocker changes the requested result.

Read `references/clean-base-prepass.md` first; it defines the mandatory preprocessing question and both working-base branches. Then read `references/remotion-semantic-director.md` before any Remotion semantic analysis and `references/auto-semantic-director.md` for automatic ingestion and working-timeline timestamping. After the semantic scene is stable, read `references/semantic-component-library.md` and route only through the approved entries in `assets/semantic-component-contract.json`. Read `references/reference-first-integration.md` before planning any H3 shot; it is the active H3 B-roll integration contract and overrides manual confirmation gates and whole-video editorial routing in the preserved upstream documents. Read `references/layer-rules.md` completely before editing foreground data or animation components. Read `references/foreground-rhythm-compiler.md` before compiling the final foreground timing. Read `references/sfx-library.md` for every new foreground video, even when the user does not explicitly request SFX. Plan restrained action cues by default; honor an explicit request for a silent/no-SFX treatment. Read `references/visual-space-director.md` before choosing placement. The legacy 29+5 renderer pack and its routing documents have been archived out of this Skill; do not look for `renderer-pack.md`, `scene-component-contract.md`, `semantic-extension-routing.md`, or `assets/remotion-renderer-pack`. For any H3 shot, also read `references/h3-fullscreen.md`, `references/h3-visual-routing.md`, `references/h3-duration-director.md`, `references/h3-official-prompt-protocol.md`, and `references/h3-five-mode-prompt-compiler.md`. The duration director is mandatory after selecting the H3 candidate and motion pattern but before frame generation, phase writing, prompt compilation, or workflow submission. The five-mode compiler is mandatory for T2VA, I2VA, L2VA, FL2VA, and Ref2VA. Consult `references/upstream-reference-first/motion-pattern-library.md` for M01-M10 and only the composition, color, material, attention, and motion-mechanism parts of `references/upstream-reference-first/visual-dna.md`. Do not import the upstream A/E/R/M/G responsibility map, visual master plan, editorial-routing hierarchy, or production-queue system. The new semantic component library is curated independently from the preserved legacy renderer pack; reference-first remains an H3-only enhancement module.

## Workflow

0. Ask whether to preprocess the raw recording, then establish the only downstream timing authority.
   - Inspect the raw source and record its exact encoded width, height, frame rate, duration, rotation metadata, and audio streams. Preserve the raw file untouched.
   - Before cut detection, ASR used solely for cutting, or clean-base rendering, ask one short binary question: `是否先处理原视频（剪气口、明显口误、重复内容）？请选择：要 / 不要。`
   - Do not infer the answer or begin expensive preprocessing while waiting. If the current request already states an explicit choice, accept it and do not ask again. A choice already obtained by the edit-desk wrapper also counts as explicit and must not trigger a second question.
   - If the answer is `要`, run the fixed scripted chain in `references/clean-base-prepass.md`: `scripts/transcribe-words.py` for word-level ASR, `scripts/propose-clean-cuts.py propose` for acoustic plus linguistic candidates, review only the `待定` items in `analysis/clean-cut-review.md` and record them with `decide`, then `finalize` into `analysis/clean-edit-decisions.json`. Do not improvise another ASR tool or hand-scan the whole word list. Acoustic silence/breath detection only proposes candidate boundaries. Remove only non-semantic dead air and breath gaps, clearly abandoned retakes, obvious mistake-and-immediate-correction spans, and redundant repeated phrases. Preserve intentional rhetorical pauses, emotional timing, hesitation that carries meaning, and every uncertain phrase. Write `analysis/clean-edit-decisions.json`, render `media/clean-base.mp4`, write `analysis/cut-map.json`, regenerate or validate clean-base ASR, and set the clean base plus clean-output milliseconds as `workingBase` and `workingTimeline`.
   - If the answer is `不要`, do not cut, transcode, remux, or render a replacement base plate. Set the raw source itself and its original milliseconds as `workingBase` and `workingTimeline`. Use a reliable same-folder subtitle or word-timing file when available; otherwise transcribe only for semantic timing. Do not create or apply a cut map in this branch.
   - Preserve the selected working base's exact encoded width and height. Do not scale, crop, pad, stretch, reframe, or substitute a default 1080p/4K/16:9/9:16 canvas. Record the choice as `analysis/preprocessing-choice.json` so all later stages and resumptions use the same branch.
   - From this point onward, only the selected `workingBase` and `workingTimeline` may drive the background, subtitles, semantic anchors, materials, H3 retiming, SFX, and rendering. Never mix raw-source timestamps with clean-output timestamps.

1. Inspect the selected working base, its folder, and current Remotion files.
   - Start when a readable primary video exists. Do not ask the user to create or refine segmentation markdown.
   - Discover optional companion transcripts, scripts, subtitles, screenshots, recordings, and other media in the raw video's folder according to `references/auto-semantic-director.md`, then align every timed companion artifact to the selected `workingTimeline`. Remap through the cut map only in the `要` branch.
   - Extract the actual spoken timeline from the selected `workingBase` audio. Use a companion script to correct recognition text and terminology, never as fabricated timing. When speech and script differ, the recorded speech on the working base controls content order and timing.
   - Generate the word-timed transcript and the Section -> Foreground Scene -> Spoken Beat hierarchy internally. Give every Section one primary rhetorical role, then analyze each Foreground Scene through the independent real-object, information-relationship, and memory layers in `references/remotion-semantic-director.md`.
   - Complete `analysis/foreground-plan.json` through this three-layer Remotion semantic director. In the same Foreground Scene analysis, plan the complete structural expression and actively select contextual explanations that add reading value; follow `references/remotion-semantic-director.md` section 3.4. A complete structure is not a reason to stop, and a supplement need not be indispensable. Do not defer this to a second enrichment/director pass. The plan remains the whole-video source of truth for titles, key information, structured knowledge, screenshots, recordings, documents, websites, other external material, placements, and SFX. Do not create a second director that reallocates those responsibilities.
   - After the foreground plan is stable, review every Foreground Scene using `references/reference-first-integration.md` and save the compact decisions/reasons in `analysis/h3-opportunity-review.json`. Derive its accepted opportunities into the compatible `selected` list in `analysis/h3-candidates.json`. Each candidate records its exact spoken anchor, visual purpose and benefit, observable setup/action-or-reveal/closing state, one motion pattern, meaningful visible `strongEvents` with absolute narration timestamps, whether it is a true continuous process, and the retained foreground event IDs. A meaningful reveal can count as an event; decorative camera motion and the final hold cannot. Do not delete, demote, or reroute foreground, or treat its completeness as a veto on H3.
   - Analyze the complete requested video by default. A request for one range or one segment limits rendering scope, not semantic accuracy.

2. Convert the internally generated semantic timeline into composable visual layers.
   - Keep the semantic plan component-agnostic until Section boundaries, Foreground Scene boundaries, Spoken Beats, and all three layer payloads are stable. Do not emit `viewerNeed`, and do not collapse a whole scene into one component-seeking `semanticIntent`.
   - A Foreground Scene may activate the real-object layer, the information-relationship layer, the memory layer, or any combination. Select zero or one information relationship for the scene. Choose `independent`, `simultaneous`, `progressive`, or `handoff` as its layer-composition mode and preserve exact spoken anchors for every participating layer. Two or three active layers may retain their intended size, contrast, and motion at the same time. Coordinate them through measured non-overlapping zones and Spoken-Beat timing; do not invent an attention-lead, primary/supporting rank, or focus-handoff analysis.
   - Title layer: after semantic segmentation, synthesize one concise title that expresses the central thesis of each coherent section. Do not merely extract or copy a sentence, keyword, or heading from the companion script. Use the corrected recording and the full section meaning as evidence; the companion script only helps resolve wording, terminology, and context. The title may compress or paraphrase the section, but must not add an unspoken claim, result, or promise. Start it at the section's first spoken word, replace it when the next section begins, and keep the final title through the end of its section. Use user-supplied title wording only when the user explicitly locks it. Preserve an established title layout and visual identity instead of silently centering or enlarging it. For new cuts, default to `SectionTitle/referenceV2` (V2 中英标题); retain `standard` (经典标题) as a selectable alternative and preserve explicit saved choices. Follow the two-variant Title Layer contract in `references/layer-rules.md`, including the English line, section ordinal, and 38px Chinese default.
   - Run visual routing and spatial routing as two separate passes. First choose renderer candidates separately for each active semantic layer, then compose the selected layer treatments into one Foreground Scene. Only after that inspect representative source frames and choose placements from measured free regions. Never let a renderer's default column decide placement.
   - Compile the Section title grid into explicit alignment data. Every non-fullscreen event records `alignmentToken` and `visibleEdge`; the renderer aligns the actual visible surface after content measurement, not merely its host or placement zone. Fast JSON recompilation must not discard this contract.
   - For new cuts, treat `assets/semantic-component-contract.json` as the only component registry. The legacy 29+5 library has been archived and is not part of this Skill. A semantic slot still marked `pending-curation` remains unresolved instead of silently falling back to a legacy component.
   - Treat each registered `variant` as one complete, user-approved visual treatment for its semantic-compatible payload. Do not add a second hidden structure/style axis. New visual variants enter the registry only after the user reviews that individual component variant and explicitly approves it. Variants sharing one component may be switched only within the same declared semantic mode, and switching them must preserve payload, assets, placement, and timing.
   - Require a real renderer contract for every selected layer treatment: `semanticLayer`, `semanticPurpose` or `relationship` or `memoryType`, `rendererComponent`, named `variant`, `motionGrammar`, `placement`, `fallbackPlacements`, and `placementReason`. Validate approved names against `assets/semantic-component-contract.json`. Choose components only after the semantic scene is stable. One component may serve two purposes only when the registry gives each purpose a distinct mode contract; `MediaFrame/show` and `MediaFrame/recordedDemo` are the first approved example.
   - Apply a mechanism-concreteness gate inside the information-relationship layer before choosing a text treatment. When the scene's single relationship requires seeing an object analyzed, planned, split, routed, assigned, assembled, or transformed, a short label such as “导演先规划” is only a caption and cannot be the primary explanation. Prefer a deterministic process renderer that visibly carries the object through its Spoken Beats; a lightweight memory cue may remain as reinforcement when it follows the same attention hierarchy and does not obscure the mechanism.
   - Memory layer: derive foreground-worthy keywords, short statements, numbers, questions, warnings, definitions, results, verdicts, and quotations from the corrected word-timed transcript. Align every memory beat to its exact spoken anchor. Never dump raw subtitles. Route keyword/number through `ImpactToken`, claim/insight through `InsightFocus`, question through `QuestionTension`, risk/warning through `WarningBoundary`, definition through `DefinitionReveal`, status/result through `ResultLock`, verdict through `VerdictStamp`, and quotation through `QuoteFrame`. Treat "maximum three visible lines" as a rolling accumulation cap, not a one-line replacement rule: keep the first line visible when the second and third lines appear unless an explicit `hideAtMs`, semantic replacement, or collision requires removal. Render short statements as bare text by default and use content-sized lightweight glass only when reading support is needed. Preserve mobile-readable primary typography and expose editable line/highlight styling in Studio. Presentation names such as bare line, focus line, card, stamp, and keyword pop remain renderer choices rather than memory semantics.
   - `ResultLock` is a cumulative state-to-result component, not a text-replacement card. When narration first establishes a state and later gives its result, write one event containing `statusLabel`, `pendingText`, `resultLabel`, `resultText`, and an event-local `resultAtMs` aligned to the exact result Spoken Beat. Show the first compact card at event start and keep it visible through the event end. At `resultAtMs`, reveal a second equal peer card beside it; the result card may become the stronger emphasis, but it must not overwrite, remove, or reuse the first card's surface. Keep the two cards in one measured foreground group, use equal content-derived card dimensions based on the larger label/primary payload, and preserve both cards until the event exits. Use this form only for a genuine state -> result progression; an isolated result belongs in another appropriate memory treatment.
   - Card copy has one deliberately simple hierarchy. The visible card contains only a short label and one semantically compressed primary phrase. The primary phrase uses 2-5 visual units, preferably 2-4; one contiguous Latin product name, acronym, or grounded number counts as one visual unit. Do not copy a spoken sentence into the primary field. A card may have one useful exterior auxiliary phrase, but this card-local limit does not restrict scene-level contextual explanations to one small line. Route substantive contextual reading to a suitable existing treatment at normal readable foreground size. Never introduce a third text tier inside the card, and never shrink the primary font to rescue an overlong primary string. If the meaning cannot be compressed faithfully, choose a bare statement, quotation, definition, or relationship renderer instead of forcing it into a card.

  - When the spoken content contains a short high-impact term (typically 2-4 characters, or a single number/term/acronym) that anchors the current point, extract it as an independent keyword event in addition to any sentence that contains it. Independent keywords get their own showAtMs aligned to when the term is spoken, their own entry/exit animation, and a noticeably larger display size than in-sentence highlights, so they can stand on screen and break up long empty stretches where only the person is talking. Independent keywords count toward the same rolling three-line cap as key sentences. Treat independent keywords as a primary form, not an optional extra: do not let a long segment produce only one or two sentence lines and leave the rest of the screen empty.
  - Reading density: actively use grounded explanations, characteristics, uses, reasons, details, original wording, and conclusions that improve the scene's reading experience, not only indispensable facts or dramatic emphasis. Let related items accumulate while their meaning remains current. During the existing review check both clutter and unused worthwhile context; neither a complete diagram nor a short A-roll gap determines whether to add content. Do not copy every subtitle, add filler, or enforce addition-count, duration, or screen-coverage quotas.
  - Role-aware placement: when a centered presenter leaves usable space on both sides, prefer one stable lane for concrete material/evidence and the opposite lane for short key words and lightweight teaching cues. A common composition is real material on the right and cumulative key information on the left, but confirm it from representative frames. Structured diagrams may use either side according to their measured bounds. Do not send every foreground item to the same side merely because that side is dark or a renderer default points there.
  - Lightweight coexistence: do not run a separate cross-layer semantic-duplication audit. Real-object, relationship, and memory treatments may repeat or reinforce related wording when their visual functions differ. Do not dim, shrink, or remove one valid layer merely to declare another layer primary. Remove something only for an obvious accidental double-render inside the same treatment, contradictory meaning, or a physical readability collision. Time each layer's own entrance, internal progression, and exit to its Spoken Beats.
  - Foreground-free scenes are valid when none of the three semantic layers adds understanding, verification, or memory value. Preserve the speaker instead of auto-inserting a filler keyword.
  - Relationship item layer: when the selected relationship contains an explicit list, comparison, step sequence, named set, or data series, condense each spoken item into a short 2-5-unit term or phrase and preserve its individual Spoken Beat. One contiguous Latin product name, acronym, or grounded number counts as one visual unit. Do not create a second competing relationship merely because several items are present. Choose the visual form from the one selected relationship, item count, and whether the relationship is the scene's main payload.
   - Real-object layer: when the spoken content calls for a visible object, website/app/tool, document, chat/message, metric/report, person/brand/account, code/config, map/location, or real workflow, record one object purpose (`show`, `focus`, `demonstrate`, or `verify`) separately from its material type. Also record the viewer's concrete viewing task (`recognize`, `read`, `follow`, or `verify`) and the selected presentation scale. `local` and `large` are available to ordinary external material; `detailTakeover` is reserved exclusively for `MediaFrame/recordedDemo`. Route the four approved purposes exactly through `references/semantic-component-library.md`: `MediaFrame/show`, `CalloutSpotlight/aimedCallout`, `MediaFrame/recordedDemo`, or the approved `BRollStack/proofDeck|evidenceTrack` verification variants with the documented single-proof fallback. Use `evidenceTrack` when several materials must remain visibly present while each spoken proof travels into one large readable center position; use `proofDeck` when a compact front-card stack communicates the set sufficiently.
   - External screenshots, ordinary recordings/B-roll, evidence, documents, webpages, dashboards, code, and product-page captures remain information-bearing Remotion foreground, but never become full-screen merely because the viewer must read or verify them. Present them at a measured `large` scale and use semantic crop, zoom, focus, or callout inside that large foreground region when details need emphasis. Only a prerecorded product/process operation demonstration—continuous UI or process actions whose steps the viewer is meant to follow—routes to `MediaFrame/recordedDemo` and full-screen `detailTakeover`. A clip used only to recognize a product, result, person, or scene is `show`, not `demonstrate`, and remains local/large. Package these decisions inside `analysis/foreground-plan.json`; never move material selection into the H3 submodule.
   - Ground each external clip's timeline start in the Spoken Beat that introduces or requires it; source duration is not permission to start earlier. When a later semantic boundary reduces the display window, keep the grounded start, end at that boundary, and truncate the remaining source instead of back-solving an earlier start to play the whole clip. Use only a modest, still-readable speed-up when it improves pacing. Re-map material SFX to the retained source actions after any speed change and omit cues for actions that are no longer shown.
   - SFX layer: optional short sound cues tied to title changes, key sentence entries, enumeration entries, or external-material entries. Use the bundled semantic library in `assets/sfx/manifest.json`: `soft-pop` for compact text/items, `soft-whoosh` for larger material movement, `mechanical-build` for visible assembly/routing/structured-process construction, and `mechanical-lock` for completion, installation, confirmation, or a final locked state. Keep cues subtle but clearly audible on an ordinary phone speaker. Store per-cue volumes in data and expose one composition-level `sfxMasterGain` so the entire mix can be raised or lowered without editing every cue. Do not add independent audio rhythm that fights the spoken video.

3. Generate selected reference-first H3 full-screen explanation shots.
   - Run this as an additive pass after the Remotion foreground and real-object plan is complete. H3 may enrich a Foreground Scene with a concrete background action, but it must not decide whether the Section title, real-object, information-relationship, or memory-layer information survives.
   - Select H3 for a material comprehension, emotional, or memory benefit: mechanisms, concrete scenarios/metaphors, role interaction, spatial relationships, comparisons, reactions, and concept embodiment are alternative opportunities, not cumulative conditions. Do not require a physical transformation or new information beyond Remotion. Follow the truth and feasibility boundaries in `references/reference-first-integration.md`; never generate fake evidence, dashboards, comments, metrics, actual product results, or customer outcomes.
   - Keep foreground and H3 routing independent. H3 supplies a concrete scene or experience; Remotion retains exact titles, captions, labels, diagrams, structured knowledge, and external-material packaging. Showing and naming the same idea is valid reinforcement when the visual functions differ. Resolve an actually redundant treatment or readability collision without stripping the foreground plan down to bare A-roll. No shot-count minimum or maximum is implied.
   - Search the bundled/personal reference library with relationship-plus-mechanism queries. Inspect the actual source or contact sheet, then bind at most one P palette/material, one C composition/spatial, and one M motion/camera role. Record what is borrowed and what must not be copied.
   - Use the bundled starter examples and user-supplied or personal media only when the user has appropriate rights. The upstream creator library is not redistributed here. Keep `assetId`, P/C/M role, `borrow`, and `doNotCopy` only as traceability and prompt-control metadata, never as an upload gate.
   - Use `I2VA` as the reference-first default. Use `L2VA` when only the exact destination matters, `FL2VA` when both endpoints must be controlled, and `T2VA` only when a frame would not improve control or image generation is unavailable. Use `Ref2VA` when complementary visual and motion references materially improve the shot: the installed workflow requires exactly two non-endpoint reference images plus one reference video whose picture and embedded audio are both passed through the workflow. Picture 1 must be a generated current-shot-specific content/layout/style solution; Picture 2 is one complementary library or user reference; Video 1 is the authoritative M reference. Trim the M video to one coherent 2-15 second range and map its inspected beats to every current-shot phase.
   - Before generating any endpoint/reference image, run `scripts/plan-h3-duration.py` for each accepted candidate and write `analysis/h3-duration-plans/<shot>.json`. Choose 3-5 seconds for one impact/state change, 6-9 seconds for 2-4 strong events, and 10-15 seconds for a continuous 5-6-event process, then reconcile that class with the exact spoken span and motion-pattern tendency. Tighten an overbroad anchor or split a shot longer than 15 seconds/more than six strong events. Only `decisionStatus: ready` may continue.
   - For `I2VA`, `L2VA`, or `FL2VA`, generate clean 16:9 first/last frames without titles, captions, readable UI, logos, fake metrics, or watermarks. For `Ref2VA`, generate a clean current-shot Picture 1 with the same semantic specificity. Validate every endpoint and Ref2VA Picture 1 with `scripts/ensure_2k.py`; require an actual 2048x1152 PNG and inspect its semantic content rather than accepting an upscale alone. Ref2VA Picture 2 may be PNG, JPG/JPEG, WebP, or GIF at its readable source dimensions.
   - Before writing phases, lock the true information direction and choose a matching M01-M10 relationship type or `NEW`. Fill the schema-v3 `motionPatternContract` so the relationship, rationale, primary law, trigger, attention path, and completion proof become executable prompt text rather than metadata.
   - Write each schema-v3 contract from `assets/reference-first-h3-shot-template.json`. Copy the ready duration plan into it. The same selected integer must equal `durationSeconds`, `durationPlan.selectedDurationSeconds`, and the final phase endpoint. Include source anchors, mode-specific current-shot reference role, executable motion-pattern contract, P/C/M contract, three or four object-action-outcome phases, absolute narration anchor for every phase, Ref2VA beat mapping when applicable, foreground coexistence, crop safety, sound, and result hold.
   - Run `scripts/audit-reference-first-contract.py` before prompt compilation. Build the five-mode schema-v3 bundle with `scripts/build-reference-first-h3-prompt.py`; submit with `scripts/runninghub-i2v.py` through the matching bundled T2VA/I2VA/L2VA/FL2VA/Ref2VA config. The runner must inherit duration from the audited prompt bundle and write that same value into the workflow duration node. Do not rely on a config default or pass a conflicting CLI duration. A paid job with audit errors must not be submitted.
   - Inspect returned footage at 0%, 10%, 33%, 58%, 82%, and 100% for semantic adherence and, for Ref2VA, separate reference-motion adherence. A clip that explains the idea but ignores the selected M attention path, movement topology, camera/depth behavior, or settling rhythm does not pass. Change the first upstream divergence rather than accepting it as model variation.
   - Generate every H3 clip as 16:9 using the workflow JSON's native resolution selector. Do not pass source-video width, source-video height, delivery resolution, megapixel values, or `--aspect-ratio` into RunningHub. Verify that node 16 remains `16:9 (Widescreen)` with its original megapixel and multiple values.
   - Compose the returned clip as a borderless full-canvas takeover above the source video and below all required Remotion foreground layers. Use centered `object-fit: cover`; allow crop, never stretch. Keep the core subject and causal action inside the central crop-safe region.
   - Probe requested versus actual H3 duration, then create `analysis/h3-retime-plans/<shot>.json` only as a fine-adjustment layer. Place at 1.0x first; trim unusable lead/tail frames, limit speed correction to 10%, and limit a deliberate stable-result hold to 0.8 seconds. Never loop or reverse. If direct fit requires more, revise the anchor/prompt or regenerate instead of repairing a generic fixed-length clip. Never show an action or consequence before its matching clause.
   - Inspect every returned or supplied animation clip for an audio stream. Preserve useful animation sound by default and mix it below the current narration; added SFX is a separate overlay and must never replace the clip's own audio. Mute only conflicting speech, irrelevant/noisy sound, or audio the user explicitly asks to remove. When one clip is drawn more than once for visual treatment, keep all visual copies muted and render exactly one separately trimmed audio track.

   - Before compiling Remotion event data, run `scripts/compile-foreground-rhythm.py` on `analysis/foreground-plan.json` and write `analysis/foreground-plan.rhythm.json` plus `analysis/foreground-rhythm-report.json`. Pass the selected working-base frame rate. Use the rhythm-compiled plan for all downstream foreground auditing, alignment, and rendering while preserving the original plan as the semantic/spatial source. This pass must remain deterministic, idempotent, model-free, render-free, and H3-neutral.
   - Install the new curated implementation with `python scripts/install-semantic-component-pack.py <remotion-project> --sync-package --force`. Import the approved components from the installed `src/semantic-foreground-pack`.
   - Use the shared design tokens, responsive placement, deterministic motion helpers, and named variants in the semantic component pack. Do not invent per-video clones when an approved component already covers the semantic purpose.
   - The semantic-component installer also copies the bundled SFX library into `<project>/public/sfx`. Use those installed paths in cue data instead of relying on an earlier video's folder.
   - After foreground timing is compiled, review every enabled event and its internal visible beats, including titles, keyword/definition arrivals, numbers, list and process items, callouts, graphic objects, and verdict/result states. Write `analysis/sfx-cue-coverage.json` with each meaningful beat's event ID, visible timestamp, cue ID and sound timestamp, or a concrete silence reason. Follow `references/sfx-library.md`; one Section title cue does not cover later text. Share a cue for simultaneous visual beats and leave source-audio result showcases clear.
   - Preserve aesthetic coherence while allowing composition variety: one dominant focal element per event, clear type hierarchy, content-sized surfaces, restrained accents, quick settle/long readable hold/clean exit, and visually distinct variants whose geometry or state change differs materially. Establish alignment tokens from the current title and safe-area geometry, then align the visible edges of same-lane components to those tokens; placing a component inside a zone and centering it internally does not count as alignment.
   - Size text-support cards from their rendered content. A one-line card remains shallow, short statements default to bare text, and a progressive sequence reserves space only for items already spoken. Use a clear mobile hierarchy between hero content, current primary information, retained/completed primary information, and true auxiliary metadata. Never shrink a valid lower-tier primary statement into helper typography.
   - Treat content sizing as a renderer contract, not a prose preference. Every approved text-support or equal-peer state component declares `renderingContract.surfaceSizing`, marks its actual visible surface with `data-content-sized-surface`, and marks spoken primary copy with `data-primary-text`. `scripts/validate-semantic-component-pack.py` must fail when one of these contracts is missing, so the edit desk cannot sync a fixed empty card back into production.
   - Keep the background transparent by default.
   - **Hard foreground-host rule:** a component may mount in a transparent full-frame host for timing and coordinates, but that host is not automatically a visible Scene. Ordinary cards, words, diagrams, screenshots, webpages, evidence, documents, focus masks, proof decks, blur, glow, and scrims stay inside measured local/large zones. Imported RemotionUI examples remain motion/style references only. Two explicit takeover owners are allowed: H3 explanation shots and `MediaFrame/recordedDemo` operation demonstrations. No other real-object purpose, viewing task, component, or variant may use `detailTakeover`. A recorded operation demo may cover or replace the presenter because the operation itself is the primary information; title, captions, and at most two lightweight timed callouts remain above it.
   - Add an optional background-video mode for preview and composite export. For full-video work, keep working-timeline timestamps absolute. For one-range work, set the composition duration to `rangeEndMs - rangeStartMs`, seek the working-base video to `rangeStartMs`, and convert all absolute subtitle/visual timestamps into local times with `localMs = absoluteMs - rangeStartMs`.
   - Do not physically cut the original video into per-segment files unless the user asks. Use Remotion timeline offset/seek props so the segment composition shows the matching source-video range.
   - Set the Remotion composition width and height to the selected working base's exact encoded resolution. ## Do Not

- Do not run the semantic director, component router, H3 director, or final Remotion timing against the raw recording after a clean cut has been created. When preprocessing was declined, the unchanged raw recording is the selected working base and is valid for all later stages.
- Do not cut solely from waveform amplitude, silence duration, or an arbitrary speed quota. Acoustic analysis proposes boundaries; word timing and meaning authorize them.
- Do not reuse raw subtitle timestamps unchanged after removing time. Remap them through `analysis/cut-map.json` or regenerate them from the clean base plate.
- Do not change encoded width or height while creating the clean base plate, even when the source is larger than 1080p.
- Do not keep an unrelated permanent explanation strip across the video or create a fourth semantic layer. This does not prohibit scene-scoped contextual reading through the existing layers; keep each expression readable and grounded.
- Do not place a sentence, clause, or more than five visual units in a card's primary-text field. A card owns only its label and short primary phrase; optional auxiliary wording sits outside the card in small type.
- Do not add a third copy tier inside a card. Do not solve overlong card copy by wrapping it into a headline block or reducing the primary font size.
- Do not accidentally render the same item twice inside one treatment. Related wording may reinforce across structure, context, and real material when it serves a reading function; do not delete useful content merely for lexical overlap.
- Do not invent enumeration items. Use only items explicitly supported by the corrected spoken transcript or a matching, recorded companion script passage.
- Do not require, request, or wait for user-authored segmentation markdown. Generate all segmentation and title timing internally from the video.
- Do not treat an untimed companion script as timing truth. Align it to recognized speech and preserve omissions, additions, repetitions, and reordered clauses from the recording.
- Do not make every key sentence a card. Short key sentences should be bare text with keyword highlights; reserve lightweight glass cards for medium/long sentences that need reading support.
- Do not default to a large parent card that gradually fills with three child cards. Use a grouped feature card only when that group is the main visual and semantically tight.
- Do not position key sentence cards with fixed y-values that can overlap. Lay them out as a stacked queue using each row's actual height plus a consistent gap.
- Do not give key sentence cards fixed height, fixed `min-height`, or large preset vertical padding. Card height must be content-sized from text line-height plus tight padding.
- Do not hardcode key sentence font size, font family, color, line height, icon size, or icon color only in the renderer. These must be editable per line through data/props.
- Do not force every line to be tuned from scratch. Provide named style presets plus per-line overrides so Studio editing stays practical.
- Do not color an entire key sentence when only a keyword should be emphasized. Use editable `highlights` spans with per-span color, font size, and font weight.
- Do not let enlarged highlight spans clip or overlap. Recompute line and card measurements when a highlight changes size or weight.
- Do not use colored text badges, numbers, or subtitle-like blocks as fake icons before key sentences. Use a real semantic icon/symbol or omit the icon. For peer collection cards, explicitly serialize `items[].icon` from the shared SVG vocabulary (or `none`); no first-character fallback is allowed. See the Collection contract in `references/semantic-component-library.md`.
- Do not make every visual trigger loud. SFX is optional feedback, not a beat track; dedupe or soften cues when several entries happen close together.
- Do not confuse lower hierarchy with helper typography. A secondary primary statement, step, tag, state, or short term must still have phone-readable visual weight; only actual metadata, English labels, ordinals, and definitions belong in the small tier.
- Do not force every enumeration into one heavy card style. Match the form to enumeration type, count, and priority.
- Do not let key sentence lines accumulate forever. Same-screen middle-layer key sentences are capped at three lines, but the cap means a rolling three-line window, not showing only the newest line.
- Do not force every external material into the same right-side slide-in frame.
- Do not shrink information-bearing screenshots, recordings, documents, dashboards, code, or product interfaces into decorative side thumbnails. Do not protect the presenter's visibility at the cost of making the referenced material unreadable.
- Do not grant `detailTakeover` to screenshots, webpages, documents, dashboards, evidence, code, still images, ordinary B-roll, proof decks, or `MediaFrame/show`, even when their viewing task is `read` or `verify`. Keep them local/large and use semantic crop, zoom, focus, or callout.
- Do not keep a prerecorded product or process operation demonstration in a small picture-in-picture panel. Route it as `MediaFrame/recordedDemo` and use full-screen `detailTakeover`. If a clip is used only for recognition, classify it as `show` rather than weakening the recorded-demo rule.
- Do not confuse a transparent full-frame coordinate host with a full-screen visual component. Never let a semantic foreground component paint an opaque page background, globally dim the source video, or inherit a RemotionUI full-scene layout.
- Do not use `right`, `rightSafe`, or `topRight` as an implicit default. Choose a side only after source-frame occupancy analysis and store the reason.
- Do not satisfy visual diversity by renaming the same white-text/underline or glass-card renderer. A different mode must create a visibly different composition, hierarchy, or motion.
- Do not create a local one-off implementation of an approved semantic component merely to save time. Improve the new reusable pack and keep project data declarative.
- Do not choose variants randomly or rotate through them mechanically. Semantic fit and available space decide first; recent repetition only breaks ties.
- Do not route an uncurated semantic slot to the legacy component library. Leave the component decision pending until its style has been reviewed and approved.
- Do not approve a component from source code alone. Render it over a representative talking-head frame and inspect it at phone-viewing size.
- Do not keep an external material presentation on screen for an entire long segment unless explicitly requested.
- Do not hardcode missing real images or videos as final assets. Keep them replaceable through explicit paths in data.
- Do not render H3 as a small card, rounded picture-in-picture, framed panel, or 4:3 insert. H3 is a borderless full-screen 16:9 takeover layer in this skill.
- Do not suppress necessary Remotion titles, key information, structured knowledge, or captions merely because H3 is active. Recompose and add a restrained readability scrim so the layers coexist without collision.
- Do not import the upstream project's A/E/R/M/G whole-video responsibility map, evidence hierarchy, visual master plan, editorial routing, or general motion-production queue. Those systems compete with this Skill's established Remotion director and make the result sparser.
- Do not move screenshots, recordings, documents, webpages, proof, or other real external material out of `analysis/foreground-plan.json`. They remain first-class Remotion visual events and may coexist with titles, keywords, annotations, and H3 B-roll.
- Do not treat H3 selection as permission to delete or demote existing foreground events. H3 is an additive B-roll enhancer; preserve the original plan and narrow only a genuinely duplicated label or illustrative detail after checking the complete composition.
- Do not ask RunningHub to generate at the source-video or final-render resolution. Preserve the workflow JSON's original generation resolution and scale only during Remotion composition.

Pause only for a real blocker that changes meaning, cost authorization, workflow availability, or required external assets.
- Use starter and user-provided materials only within their applicable licenses; the restricted creator library is optional and absent from this distribution.
- Do not call a shot reference-first merely because an image was attached. A reference contract must bind a specific P, C, or M mechanism and state what is not copied.

## Common Files

### Shared inner-card edit contract

- The authoritative semantic foreground pack exports `EditableElementBridge` and stable inner-surface IDs. Default autonomous renders omit `elementOverrides` and remain visually unchanged.
- Human-assisted projects may add `event.elementOverrides[stableCardId] = {x, y, scale, color}`. These are presentation-only overrides layered after semantic/component selection. Whole-component placement and accent color remain independently editable.
- Relationship connectors are computed from the current endpoint surfaces whenever inner overrides exist. Never bake connector endpoints into the director JSON, and never fork a second component renderer inside the edit desk.
- Recomputed connectors preserve each component's reviewed route grammar and dashed/glow treatment; they do not collapse curved causal, relay, radial, loop, or board motion into generic straight segments. Only actual connector layers may be suppressed, never every SVG descendant. Connector color follows an explicitly recolored adjacent card, otherwise that card's original reviewed accent.
- An inner-card color override propagates to that card's complete accent system—including labels, sequence badges, icons, dots, accent bars, borders, and SVG fill/stroke—while neutral body copy remains unchanged.
- Every card owns an isolated accent-variable scope so one override cannot recolor siblings, nested cards, parent groups, or unrelated branches. Keep the native connector visible until a replacement route is ready, and exclude that derived route from subsequent native-connector discovery.

## Output Notes

Use ProRes 4444 for transparent compositing:

```powershell
npm run build:prores
```

Use MP4 for source-video preview or direct composite export:

```powershell
npx remotion render src/index.ts CaptionCards out/preview.mp4 --codec=h264 --pixel-format=yuv420p
```

Keep two export paths when a source video is present:

- Transparent foreground export: no background video, alpha preserved.
- Composite export: original video range as the background plus the foreground animation, suitable for direct review or publishing.
- Composite export with SFX: preserve source-video audio and mix SFX quietly under speech.
- Composite export with inserted animation: preserve the animation's useful original audio on its exact trimmed interval, then mix optional SFX as an additional layer rather than as a substitute.
